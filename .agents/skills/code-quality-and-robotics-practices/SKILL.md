# 代码质量、架构设计与机械臂工业实践准则 (Code Quality & Robotics Best Practices)

本 Skill 沉淀了现代软件工程高内聚低耦合原则、类设计逻辑以及工业机械臂开发的核心准则。后续在任何任务执行中，只要涉及代码阅读、修改、重构或机械臂硬件交互，均必须主动对齐本规范。

---

## 第一部分：代码质量、重构与防退化原则 (Code Quality & Refactoring)

### 1. 死代码与废弃逻辑的彻底清理
- **无死代码**：在开发或审查过程中，若发现未引用的函数、未使用的变量、已经废弃的兼容别名、被注释掉的陈旧逻辑，必须果断彻底清理，不得保留“僵尸代码”。
- **DRY 原则 (Don't Repeat Yourself)**：
  - 严禁功能重复：若同一判定逻辑（如 `is_spraying_on`、状态转换、坐标系变换、位姿格式化）在多处出现，必须抽象为单一纯函数并下沉到公共模块。
  - 避免“平行实现”：统一数据结构入口，如 `RobotPose` 统一承担位姿互转，避免在业务代码各处自行 `[pose[0], pose[1]...]` 手工切片。

### 2. 提升内聚度与扇入度 (High Cohesion & High Fan-In)
- **高内聚 (High Cohesion)**：
  - 一个函数只做好一件事，一个类只负责一个核心职责领域。
  - 数据与操作高度绑定：操作位姿的算法归属于位姿模块，控制协议解析归属于驱动模块，任务流转归属于服务层。
- **高扇入、低扇出 (High Fan-In, Low Fan-Out)**：
  - 核心通用能力（如底层通信、位姿数学、状态广播、DO控制）应当设计为高扇入（被多个业务模块稳定复用），避免每个模块各自造轮子。
  - 业务层要降低扇出，避免一个函数依赖十几二十个外部不相关模块，降低脆弱性和耦合度。

### 3. 防御性编程与 Bug 预防
- **严格边界与范围校验**：
  - 凡是外部输入（API 入参、配置文件、网络数据包），必须进行范围合法性校验（例如 DO 端口号必须验证 `1 <= index <= 16`，速度百分比 `1 <= speed <= 100`），非法输入必须快速失败（Fail-fast）并给出清晰报错，严禁带病运行。
- **保护并发与资源竞争**：
  - 在嵌入式/多核平台（如 RK3588）上，杜绝在主循环/异步事件循环中执行耗时大运算（如万行文本纯 Python 解析），应使用 C 扩展工具（如 `fast_yaml_load`）或后台线程隔离。

### 4. 保持代码可读性与精准注释 (Readability & Meaningful Comments)
- **KISS 原则 (Keep It Simple, Stupid)**：优先选用简单、直观、扁平的实现，避免过度设计。
- **保留关键领域注释**：
  - 代码注释不可删除！重点保留包含**物理意义、量纲单位（mm, deg, rad, m/s, mm/s）、通信协议格式、坐标系约定以及边界条件**的关键注释。
  - 函数签名应附带完整的类型注解 (`typing`)。

## 第二部分：面向对象与类设计架构规范 (Class Design & Software Architecture)

### 1. 软件三层架构与职责边界
- **驱动层 (Driver Layer, e.g., `BaseRobotDriver`, `DobotDriver`)**：
  - 职责：只负责与物理硬件进行协议层一问一答、状态轮询与端口数据封包解包。
  - 规则：驱动层不感知具体业务概念（不感知喷涂、不感知工件模板、不感知用户交互），仅提供基础的运动队列、点动、I/O 开关和动力学监控。
- **服务层 (Service Layer, e.g., `RobotService`)**：
  - 职责：单例模式（Singleton）管理硬件生命周期、多客户端 WebSocket 状态广播、报警缓存、任务执行状态编排。
  - 规则：为上层业务提供线程安全、异常隔离的高层 API。
- **路由/API 层 (Presentation/API Layer, e.g., `api.py`)**：
  - 职责：处理 HTTP/WebSocket 协议解析、安全校验、参数防御校验、将业务任务转派给服务层。

### 2. SOLID 原则在工业软件中的落地
- **单一职责原则 (SRP)**：
  - 例如将喷涂 DO 的开关逻辑、轨迹航点的几何插补、相机的点云重构严格分离，各司其职。
- **开闭原则 (OCP)**：
  - 驱动抽象基类 `BaseRobotDriver` 定义标准契约，后续新增新品牌机械臂（如 Inexbot、UR 等）只需继承基类实现对应虚方法，而无需改动上层业务逻辑。
- **里氏替换原则 (LSP)**：
  - 所有子类驱动的方法签名、参数单位和返回值含义必须与基类 100% 保持一致，调用方无需针对具体型号写特化 `if is_dobot` 分支。
- **依赖倒置原则 (DIP)**：
  - 高层服务依赖驱动抽象接口，通过工厂方法（`get_robot()`）装配具体驱动实例。

## 第三部分：机械臂行业的工业级最佳实践 (Robotics Industry Best Practices)

### 1. 运动指令与 I/O 动作的同步控制（最核心工艺准则）
- **队列指令 (Queued Commands, 如 `DO`)**：
  - **适用场景**：连续轨迹喷涂中的起喷、关喷、跳段空走切换。
  - **核心原理**：DO 指令必须与 MoveL/MoveJ 等运动插补指令一同推入控制器的底层算法队列中，由底层插补器在到达特定物理空间坐标时硬件级同步触发。
  - **严禁行为**：在连续轨迹喷涂段间绝对不能为了开关 DO 而强行停止机械臂或使用立即指令，否则会破坏连续平滑过渡（CP），导致工件表面停留烧焦、滴漆或出料不均。
- **立即指令 (Immediate Commands, 如 `DOExecute`)**：
  - **适用场景**：用户界面手动点动开关、急停（E-Stop）、轨迹异常中断保护、程序退出清理。
  - **核心原理**：绕过当前算法队列立刻作用于物理电气接口，确保安全响应时延处于毫秒级。

### 2. 连续平滑过渡 (Continuous Path / CP / Blending)
- 机械臂执行密集航点（Waypoints）或分段轨迹时，各分段在控制器中必须保持平滑过渡比例（如 CP=100 或 CP=50）。
- 仅在整条路径执行到**最后一个目标点**时才下发等待就位（`wait=True`），全流程保证速度连续、无机械冲击。

### 3. 机械臂运行状态判定的统一标准 (Idle vs Moving vs Error)
- **状态源唯一性**：
  - 必须以机械臂底层控制器实时反馈的运行状态（如 Dobot 30004 端口偏移 1028 的 `running_status`）作为唯一真理：
    - `status === 0`：机械臂空闲 / 停止 (Idle)
    - `status === 1`：机械臂正在运行 / 走轨迹 (Moving / Running)
    - `status === 2`：机械臂处于暂停状态 (Paused)
- **互锁与防误触（Interlock Protection）**：
  - 任何运动指令下发前必须检查机械臂状态；
  - 当机械臂正处于物理运动中（`status !== 0`），前端界面的所有执行按钮、回零按钮、点动按钮必须**在 UI 层面和 API 校验层面双重置灰锁定**，绝不允许并发提交导致指令乱序或冲撞。

### 4. 严格的坐标系与量纲规范 (Coordinate Frames & Units)
- **坐标系清晰无歧义**：
  - **Base Frame (基座坐标系)**：所有空间绝对轨迹点必须以 Base 坐标系为基准表示。
  - **Tool Frame / TCP (工具坐标系)**：喷头末端中心点必须通过标定精确配置到指定 `robot_tcp_id`（如 `gripper_tip_link` 或 `laser_head_link`）。切换工具编号需在机械臂完全静止时下发，并确认控制器生效。
- **量纲统一**：
  - 长度距离：系统内部统一采用毫米 `mm`；
  - 旋转姿态：底层数学库、变换矩阵、欧拉角计算**统一采用弧度 `rad`**；与机械臂通信协议封包时**显式换算为度 `deg`**，变量命名强制加上 `_deg` 或 `_rad` 后缀消除二义性。

### 5. 故障安全设计 (Fail-Safe & Graceful Degradation)
- **关断优先 (Fail-Close)**：
  - 机械臂在任何情况下发生异常（包括断网、越限、逆解失败、用户点击急停、进程被强杀），**首要安全动作必须是关闭喷涂 DO (置 0)**，杜绝原料失控泄漏。
- **通信缓冲区自愈**：
  - 每次开始新的大动作（如 `go_home`）前，主动执行 `_discard_pending()` 清理套接字接收缓冲区中的迟到残留数据，防止一问一答协议发生错位死锁。

## 第四部分：国际化与严格全英文界面准则 (Strict English-Only UI Interface)

### 1. 前端 UI 界面 100% 英文
- 前端页面所有的视图元素必须全部采用专业、规范、简练的英文：
  - 按钮文案（Buttons & Actions）
  - 悬浮提示（Tooltips & Popovers）
  - 状态指示与徽章（Badges & Labels）
  - 右键菜单项（Context Menus）
  - 任务状态胶囊与 HUD 显示（Capsules & HUD Pill texts）
  - 通知与弹窗信息（Toasts, Notices & Alerts）
- 严禁在任何前端用户交互界面中呈现中文字符。

### 2. 用户可见的后端广播与报错统一使用英文
- 后端向 WebSocket 客户端广播推送的执行动作描述（如 `broadcast_exec_status(action=...)`）、任务进度状态、以及向前端返回的 HTTP 异常 `detail` 报错，均属于用户直接可见内容，**必须 100% 使用英文**编写。
- 内部日志（`logger.info` / `logger.error`）可保留必要中文领域注释说明，但下发给 UI 展示给用户的字段必须为规范英文。
